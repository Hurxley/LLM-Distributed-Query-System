## 功能一：Worker 启动与注册

**目标**：每个 Worker 启动时连接自身数据库、收集元数据、向 Coordinator 注册逻辑字段信息。

### 涉及的 py 文件

```
engine/app.py          → Worker 主应用（lifespan 生命周期）
engine/db.py           → 数据库连接管理
engine/sql_builder.py  → 加载 mapping.yaml
engine/tokenizer.py    → 获取 HMAC 盐值
coordinator/app.py     → 接收注册请求
coordinator/schema_manager.py → 存储全局 Schema
```

### 函数调用链（按执行顺序）

```
┌─────────────────────────────────────────────────────────────────┐
│ engine/app.py: lifespan()                                       │
│   │                                                             │
│   ├─[1] sql_builder.load_mapping()                              │
│   │      └─ engine/sql_builder.py: _MappingCache.get()          │
│   │           读取 engines/worker_*/mapping.yaml，缓存到内存      │
│   │           返回 {worker_id, worker_name, table, fields:[...]}│
│   │                                                             │
│   ├─[2] db.get_connection()                                     │
│   │      └─ engine/db.py: get_connection()                      │
│   │           根据 DB_TYPE 环境变量创建数据库连接:                  │
│   │           · sqlite  → sqlite3.connect(只读URI模式)           │
│   │           · mysql   → mysql.connector.connect()             │
│   │           · postgresql → psycopg2.connect(RealDictCursor)   │
│   │           连接缓存为全局单例，后续复用                          │
│   │           最多重试5次（每次间隔3秒）                           │
│   │                                                             │
│   ├─[3] tokenizer.get_salt()                                    │
│   │      └─ engine/tokenizer.py: get_salt()                     │
│   │           从环境变量 SALT 读取 HMAC 盐值                       │
│   │           若未设置则抛出 RuntimeError                         │
│   │                                                             │
│   ├─[4] db.execute_scalar("SELECT COUNT(*) FROM <table>")       │
│   │      └─ engine/db.py: execute_scalar()                      │
│   │           执行全表 COUNT，获取行数（row_count）                │
│   │           同时计算全表扫描耗时（scan_latency_ms）              │
│   │                                                             │
│   ├─[5] 构建注册负载（仅逻辑字段！）                                │
│   │      遍历 mapping.fields，对每个字段生成:                     │
│   │        {logical, alias, secret, type, values}               │
│   │      注意：绝不包含 physical 列名                             │
│   │                                                             │
│   └─[6] HTTP POST → Coordinator /register                       │
│          └─ coordinator/app.py: register_worker()               │
│               └─ coordinator/schema_manager.py:                 │
│                    GlobalSchema.register_worker()               │
│                     · 存入 workers[worker_id]                    │
│                     · 建立 field_index[逻辑字段→[worker_id]]     │
│                     · 建立 alias_index[别名→逻辑字段]             │
│                     · 合并 field_details（多Worker同名字段值域合并）│
│          最多重试30次（每次间隔2秒），容忍 Coordinator 后启动       │
└─────────────────────────────────────────────────────────────────┘
```

### 每个函数的作用

| 步骤 | 文件:函数 | 作用 |
|---|---|---|
| 1 | `sql_builder.py:_MappingCache.get()` | 加载 YAML 映射文件（逻辑字段→物理列），使用类级别缓存避免重复读取 |
| 2 | `db.py:get_connection()` | 根据 DB_TYPE 创建对应数据库连接（MySQL/PostgreSQL/SQLite），单例缓存 |
| 3 | `tokenizer.py:get_salt()` | 从环境变量读取 HMAC-SHA256 盐值，所有 Worker 必须统一 |
| 4 | `db.py:execute_scalar()` | 执行标量 SQL 查询，获取行数和扫描延迟作为性能基线 |
| 5 | `app.py:lifespan()`（内联逻辑） | 从 mapping 提取仅逻辑元数据构建注册负载，剔除物理列名 |
| 6 | `schema_manager.py:register_worker()` | 将 Worker 字段信息注册到全局索引，支持后续字段路由和查询解析 |

## 功能二：全局 Schema 查询

**目标**：前端或 LLM 获取所有已注册 Worker 的字段和取值域信息，用于展示查询能力和构建 Prompt。

### 涉及的 py 文件

```
coordinator/app.py
coordinator/schema_manager.py
```

### 函数调用链

```
用户/前端 GET /api/schema
    ↓
coordinator/app.py: get_schema()
    │
    ├─[1] global_schema.get_workers_summary()
    │      └─ schema_manager.py: GlobalSchema.get_workers_summary()
    │           遍历 self.workers，为每个 Worker 返回:
    │           {name, fields:[逻辑字段名列表], row_count, scan_ms}
    │
    └─[2] global_schema.get_all_fields_summary()
           └─ schema_manager.py: GlobalSchema.get_all_fields_summary()
                遍历 self.field_details，为每个逻辑字段返回:
                {logical, type, values, secret, workers:[Worker名称列表]}
```

### 返回数据结构

```json
{
  "workers": {
    "worker_a": {"name": "人才库", "fields": ["person_token","gender",...], "row_count":1000, "scan_ms":180},
    ...
  },
  "fields": [
    {"logical": "gender", "type": "enum", "values": ["男","女"], "secret": false, "workers": ["人才库"]},
    {"logical": "person_token", "type": "token", "secret": true, "workers": ["人才库","海外库","财务库"]},
    ...
  ]
}
```

| 步骤 | 文件:函数 | 作用 |
|---|---|---|
| 1 | `schema_manager.py:get_workers_summary()` | 生成Worker维度的概览（含字段列表、数据量、性能基线） |
| 2 | `schema_manager.py:get_all_fields_summary()` | 生成字段维度的概览（含类型、值域、所属Worker） |

## 功能三：自然语言查询解析

**目标**：将用户自然语言输入（如"女性副教授的平均月收入"）转换为结构化查询 AST。

### 涉及的 py 文件

```
coordinator/app.py          → 接收查询请求
coordinator/nl_parser.py    → 核心解析逻辑（LLM + 规则回退）
coordinator/schema_manager.py → 提供字段索引和值域用于校验
```

### 函数调用链

```
用户 POST /api/query {"query": "女性副教授的平均月收入"}
    ↓
coordinator/app.py: submit_query()
    │
    ├─[1] 生成 query_id = uuid4()[:8]
    │
    └─[2] nl_parser.parse_query(user_query, global_schema)
           │
           ├─[2a] schema_manager.GlobalSchema.to_prompt_text()
           │       将全局字段信息格式化为 LLM 可读的文本描述
           │       （含Worker名、字段名、别名、值域）
           │
           ├─[2b] nl_parser.parse_with_llm(user_query, schema_text)
           │       │
           │       ├─ nl_parser._build_llm_prompt()
           │       │   将 schema_text + user_query + JSON格式规范
           │       │   组合为 LLM prompt
           │       │
           │       ├─ HTTP POST → LLM API (/chat/completions)
           │       │   发送 prompt，temperature=0.1 保证确定性
           │       │   期望返回严格 JSON: {filters:[{field,op,value}], aggregation:{field,func}}
           │       │
           │       └─ 清理 markdown 代码块 → json.loads()
           │           成功返回 parsed dict，失败返回 None
           │
           ├─[2c] 若 2b 失败 → nl_parser.parse_with_rules(user_query, global_schema)
           │       │
           │       ├─ 预定义正则模式匹配（10+种）:
           │       │   · 研究方向 (物联网|人工智能|...)方向
           │       │   · 性别 女性→gender eq '女'
           │       │   · 机构 高校/科研院所/企业 → org_type
           │       │   · 职称 教授/副教授/讲师/工程师 等
           │       │       "工程师及以上"→ title gte '工程师'
           │       │   · 海外经历 有/无海外经历
           │       │   · 留学国家 显式提取"美国或德国"→ IN ['美国','德国']
           │       │   · 获奖级别 省级以上奖励 → gte '省级'
           │       │   · 年龄 \d+岁以下→lt, \d+岁以上→gt
           │       │   · 年份 \d{4}年 → eq
           │       │   · 近N年 → gte (今年-N+1)
           │       │
           │       ├─ 聚合模式匹配（15+种）:
           │       │   · "平均月收入" → avg(monthly_salary)
           │       │   · "最高年终奖" → max(year_end_bonus)
           │       │   · "总补贴金额" → sum(allowance)
           │       │   · "人数/多少人" → count(person_token)
           │       │
           │       └─ 去重与冲突解决:
           │           相同字段 eq → 合并为 in
           │           冲突操作符按优先级保留 (in>gte/lte>gt/lt>eq>neq)
           │           gte保留范围更宽的（更小的值）
           │           lte保留范围更宽的（更大的值）
           │
           ├─[2d] nl_parser.anchor_and_validate(parsed, global_schema)
           │       │
           │       ├─ 对每个 filter 的 field:
           │       │   · alias_index 解析别名→逻辑字段名（如"性别"→"gender"）
           │       │   · field_index 路由到所属 Worker ID 列表
           │       │   · 若找不到 → _fuzzy_match_field() 模糊匹配
           │       │
           │       ├─ 对每个 filter 的 value:
           │       │   · 已知值域内精确匹配
           │       │   · 否则 _fuzzy_match_value() 模糊匹配（子串匹配）
           │       │   · IN 操作符的列表值逐个校验
           │       │
           │       └─ 对 aggregation:
           │           COUNT(person_token) 特殊处理:
           │           聚合 Worker 从筛选 Worker 派生（不需要独立路由）
           │           其他聚合字段: field_index 路由到所属 Worker
           │
           └─[2e] nl_parser.validate_parsed_query(routed)
                   检查:
                   · 每个 filter 是否有 workers（能路由到数据源）
                   · 操作符是否合法 (eq/neq/gt/gte/lt/lte/in)
                   · aggregation 是否能路由到 Worker
                     （COUNT(person_token) 例外，无需 Worker）
                   返回 (is_valid, errors[])
```

### 最终返回的 AST 结构

> **注意**：`/api/query` 仅做解析，不生成执行方案。`plans` 字段返回空数组。方案通过独立的 `POST /api/query/{id}/generate-plans` 端点生成。

```json
{
  "query_id": "a1b2c3d4",
  "query_ast": {
    "filters": [
      {"field": "gender", "op": "eq", "value": "女", "workers": ["worker_a"]},
      {"field": "title", "op": "eq", "value": "副教授", "workers": ["worker_a"]}
    ],
    "aggregation": {
      "field": "monthly_salary", "func": "avg", "workers": ["worker_c"]
    },
    "valid": true,
    "errors": []
  },
  "parsed_by": "llm",  // 或 "rules"
  "plans": []           // 空 — 方案由 /generate-plans 端点生成
}
```

| 步骤 | 文件:函数 | 作用 |
|---|---|---|
| 2a | `schema_manager.py:to_prompt_text()` | 将全局字段信息格式化为 LLM prompt 用的文本 |
| 2b | `nl_parser.py:parse_with_llm()` | 调用 LLM API 进行语义解析，返回结构化 JSON |
| 2c | `nl_parser.py:parse_with_rules()` | LLM 不可用时的正则规则回退，覆盖10+种查询模式 |
| 2d | `nl_parser.py:anchor_and_validate()` | 字段路由（别名解析+Worker定位）+ 值域校验 |
| 2e | `nl_parser.py:validate_parsed_query()` | 最终合法性检查（路由完整性、操作符合法） |

## 功能四：查询计划生成与排序

**目标**：根据解析出的 QueryAST，穷举所有合法的 DAG 执行计划，估算每个方案的成本，排序后返回 Top 4。

### 涉及的 py 文件

```
coordinator/planner/orchestrate.py   → 编排主流程
coordinator/planner/precheck.py      → 预查各Worker命中数
coordinator/planner/enumeration.py   → 穷举所有合法计划拓扑
coordinator/planner/generation.py    → LLM辅助生成计划
coordinator/planner/prompt.py        → 构建LLM prompt
coordinator/planner/cost_model.py    → 成本估算模型
coordinator/planner/description.py   → 生成用户友好描述
coordinator/planner/validation.py    → 计划验证/修复/去重
```

### 函数调用链

```
前端点击"生成对比方案" → POST /api/query/{id}/generate-plans
    ↓
coordinator/app.py: generate_plans()
    ↓
coordinator/planner/orchestrate.py: generate_and_rank_plans(query_ast, workers_summary, worker_urls)
    │
    ├─[1] precheck.run_precheck(query_ast, worker_urls)
    │      └─ planner/precheck.py: run_precheck()
    │           遍历每个有筛选条件的 Worker:
    │             HTTP POST → Worker /count {"predicates":[...]}
    │             获取该 Worker 在给定条件下的命中行数
    │           所有 Worker 并行查询 (asyncio.gather)
    │           失败时回退为预估值 100
    │           返回 {"worker_a": 85, "worker_b": 42, ...}
    │
    ├─[2] enumeration._enumerate_all_plans(query_ast, workers_summary, precheck_counts)
    │      └─ planner/enumeration.py: _enumerate_all_plans()
    │           │
    │           ├─ 情况A: 无筛选Worker
    │           │   → 1个计划: aggregate → compute（直接统计，无需筛选）
    │           │
    │           ├─ 情况B: 1个筛选Worker
    │           │   → 1个计划: filter(单Worker) → aggregate → compute
    │           │
    │           └─ 情况C: 2+筛选Worker → 穷举所有拓扑:
    │               │
    │               ├─ 并行过滤器 (concurrent_group=1):
    │               │   · 求交在 coordinator → P_并行_中心求交
    │               │   · 求交在 filter worker A → P_并行_A本地求交
    │               │   · 求交在 filter worker B → P_并行_B本地求交
    │               │   · 求交在 aggregate worker → P_并行_聚合节点求交
    │               │
    │               └─ 串行过滤器 (全排列):
    │                   · filter顺序 A→B  ×  求交位置 (coord/A/B/agg)
    │                   · filter顺序 B→A  ×  求交位置 (coord/A/B/agg)
    │
    ├─[3] generation.generate_plans_with_llm(query_ast, workers_summary, precheck_counts)
    │      └─ planner/generation.py: generate_plans_with_llm()
    │           │
    │           ├─ planner/prompt.py: _build_plan_prompt()
    │           │   构建详细提示词，包含:
    │           │   · 查询结构 + Worker信息 + 预查命中数
    │           │   · 关键约束（filter/aggregate不能放coordinator等）
    │           │   · 4种方案模板（P1并行 P2串行A→B P3串行B→A P4数据下推）
    │           │
    │           ├─ HTTP POST → LLM API
    │           │   期望返回含4个 plan 的 JSON
    │           │
    │           ├─ 若返回不足2个 → 用 _generate_plans_rule_based() 补充
    │           │
    │           └─ validation._validate_and_repair_plan() 逐个验证修复
    │
    ├─[4] validation._merge_plans(existing_plans, llm_plans)
    │      └─ planner/validation.py: _merge_plans()
    │           用 _plan_topology_signature() 计算每个计划的拓扑签名
    │           签名组成: 每个stage的(type, location, concurrent_group, 依赖关系)
    │           签名相同 = 相同拓扑 → 去重
    │           LLM特有的新拓扑保留
    │
    ├─[5] enumeration._optimize_coordinator_count(plan, query_ast)
    │      └─ planner/enumeration.py: _optimize_coordinator_count()
    │           当 aggregation 为 COUNT(person_token):
    │           · 移除 aggregate 阶段（不需要发到Worker聚合）
    │           · compute 阶段直接依赖上游求交结果
    │           · compute 阶段标记 coordinator_count=True
    │             执行时直接 len(tokens) 计数，无需数据库查询
    │
    ├─[6] validation.repair_execution_plan(plan, query_ast, valid_worker_ids)
    │      └─ planner/validation.py: repair_execution_plan()
    │           （已从功能五挪至此处，在成本估算前完成）
    │           │
    │           ├─ Step1: 填充各stage的predicates和agg信息
    │           │   · filter stage ← 从query_ast取对应Worker的filter条件
    │           │   · aggregate stage ← 填充agg_field, agg_func
    │           │
    │           ├─ Step2: 移除空谓词的filter stage（无筛选条件的Worker不参与）
    │           │
    │           ├─ Step2b: 合并同一Worker上的重复filter stage
    │           │   LLM可能为同一Worker的多个条件各生成一个stage
    │           │   合并为一个stage（predicates合并去重）
    │           │
    │           ├─ Step3: 更新依赖关系（移除被删stage的引用）
    │           │
    │           ├─ Step3.5: 移除无效的intersect阶段（只剩<2个有效输入→纯透传）
    │           │
    │           └─ Step4: 自动插入缺失的intersect阶段
    │               当2+个不同Worker的filter但没有intersect时自动补入
    │
    ├─[7] cost_model.compute_cost(plan, workers_summary, precheck_counts)
    │      └─ planner/cost_model.py: compute_cost()
    │           （在已修复的干净计划上估算，一次就准）
    │           对每个 stage 计算精细耗时:
    │           │
    │           ├─ Filter阶段:
    │           │   DB扫描 = scan_ms × (命中数/总行数) + 5ms
    │           │   网络传输 = RTT + 命中数 × 每Token传输延迟(0.005ms)
    │           │
    │           ├─ Intersect阶段:
    │           │   求交计算 = 3ms (哈希集合交集)
    │           │   输出Token数 = min(输入大小) × 50%重合率
    │           │   若非coordinator侧 → +RTT
    │           │
    │           ├─ Aggregate阶段:
    │           │   DB扫描 = scan_ms × 0.4 (热缓存)
    │           │   HMAC匹配 = row_count × 1μs/行
    │           │   网络 = RTT + (非colocated时) Token传输
    │           │
    │           ├─ Compute阶段: 固定1ms
    │           │
    │           └─ 汇总: 并发组取max + 串行阶段求和 = 总耗时
    │           同时估算出口数据量 (egress_bytes)
    │
    ├─[8] description._generate_friendly_description(plan, workers_summary)
    │      └─ planner/description.py: _generate_friendly_description()
    │           从 plan.stages 推导拓扑类型:
    │           · 无filter → "直接统计方案"
    │           · 单filter → "单节点查询 — 人才库统一筛选"
    │           · 并行+coordinator求交 → "并行查询 — 2个数据源同时过滤"
    │           · 并行+非coordinator求交 → "数据下推 — 财务库本地求交"
    │           · 串行 → "串行查询 — 先查人才库"
    │           生成中文数字步骤:
    │           "第一步：同时在「人才库」和「海外库」中各自查找..."
    │           "第二步：在中心节点比对各方匿名标识，取交集..."
    │           "第三步：将交集传入「财务库」，计算所需统计..."
    │           "第四步：在中心节点汇总结果，得出最终答案"
    │
    ├─[9] cost_model.rank_plans(all_plans)
    │      └─ planner/cost_model.py: rank_plans()
    │           按 estimated_cost_ms 升序排列
    │           plans[0].recommended = True
    │
    ├─[10] 按 friendly_description 去重
    │      描述相同 = 用户视角同一方案 → 只保留最便宜的（第一个）
    │
    ├─[11] 重新编号为 P1, P2, P3, P4...
    │
    └─[12] 返回 Top 4
```

| 步骤 | 文件:函数 | 作用 |
|---|---|---|
| 1 | `precheck.py:run_precheck()` | 并行向各Worker查询筛选命中数，为成本估算提供数据 |
| 2 | `enumeration.py:_enumerate_all_plans()` | 穷举所有合法DAG拓扑（并行×求交位置 + 串行排列×求交位置） |
| 3 | `generation.py:generate_plans_with_llm()` | LLM辅助生成计划（失败时规则回退补充） |
| 4 | `validation.py:_merge_plans()` | 按拓扑签名去重合并枚举+LLM的计划 |
| 5 | `enumeration.py:_optimize_coordinator_count()` | COUNT(person_token)优化：跳过聚合Worker，主控直接计数 |

| 11-12 | `orchestrate.py`（内联） | 重编号 + 返回Top4 |

## 功能五：查询执行

**目标**：用户选择执行方案后，Coordinator 调度各 Worker 按 DAG 拓扑执行筛选、求交、聚合，最终汇总返回结果。

### 涉及的 py 文件

```
coordinator/app.py                → 执行入口
coordinator/planner/validation.py → 执行前计划修复
coordinator/scheduler.py          → DAG调度器
engine/app.py                     → Worker端点（/filter, /aggregate, /count）
engine/sql_builder.py             → 逻辑谓词→物理SQL
engine/db.py                      → 数据库查询执行
engine/tokenizer.py               → HMAC-SHA256盲化
engine/egress_filter.py           → 出口PII扫描
```

```
    │           │       │  │   │   min/max → total_min/total_max│
    │           │       │  │   │                               │
    │           │       │  │   └─ egress_filter.wrap_response()│
    │           │       │  │                                    │
    │           │       │  返回 {sum, count, min, max, value, func}│
    │           │                                              │
    │           │ D. type='compute'                            │
    │           │    └─ _do_compute(stage)                     │
    │           │       (纯Coordinator侧，无HTTP调用)            │
    │           │       收集所有上游aggregate结果:              │
    │           │       · count → sum(total_count) 或直接计数tokens│
    │           │       · sum   → sum(total_sum)               │
    │           │       · min   → min(all mins)                │
    │           │       · max   → max(all maxs)                │
    │           │       · avg   → 平均各Worker的value          │
    │           │       · coordinator_count → len(tokens)      │
    │           └──────────────────────────────────────────┘
    │
    ├─[4] 推送 "query_complete" WebSocket事件
    │      {total_elapsed_ms, result, estimated_ms, stage_times, stage_sql}
    │
    └─[5] 返回最终结果给HTTP客户端
           {query_id, plan_used, total_ms, result, estimated_ms, accuracy, stage_times, stage_sql}
```

## 功能七：API 认证与安全

**目标**：保护非公开 API 端点，防止未授权访问。

## 功能八：隐私保护（HMAC 盲化 + 出口过滤）

**目标**：确保原始身份证号永不离开 Worker，即使程序 Bug 泄露也能被出口过滤器拦截。

### 涉及的 py 文件

```
engine/tokenizer.py       → HMAC-SHA256 盲化
engine/egress_filter.py   → 出口PII扫描
engine/app.py             → 调用盲化和过滤
```

### HMAC 盲化函数调用链

```
engine/app.py: filter_endpoint() 中
    │
    ├─ 数据库查询返回 raw rows (含原始 id_card)
    │
    ├─ for row in rows:
    │     tokenizer.tokenize(row['raw_id'])
    │     └─ engine/tokenizer.py: tokenize(id_card)
    │          │
    │          ├─ get_salt() → 从环境变量 SALT 读取盐值
    │          │
    │          └─ hmac.new(salt.encode(), id_card.encode(), sha256).hexdigest()
    │               → 64字符十六进制字符串
    │               → 不可逆（无法从哈希反推原始身份证号）
    │               → 确定性（同一身份证+同盐=同一Token，支持跨库求交）
    │
    └─ 返回 仅含 Token 列表的响应
```

### 出口过滤函数调用链

```
每个 Worker 端点的 return 之前:
    ↓
engine/app.py: egress_check(response_data)
    │
    └─ engine/egress_filter.py: wrap_response(data)
         │
         ├─ _collect_strings(data)
         │   递归遍历 JSON，只收集字符串值
         │   (跳过数值和布尔值，避免 HMAC 哈希误报)
         │
         ├─ scan_response(data)
         │   正则扫描:
         │   · \b\d{17}[\dXx]\b  → 身份证号 (18位)
         │   · \b1[3-9]\d{9}\b   → 手机号
         │   · [\w\.-]+@[\w\.-]+\.\w+ → 邮箱
         │   跳过 SAFE_VALUES 白名单中的已知字段值
         │
         └─ 若发现PII:
              logger.critical("PII_LEAK_BLOCKED") + 告警
              返回 {"error":"PII_LEAK_BLOCKED", "detail":...}
             阻断响应，不返回给 Coordinator
            若通过:
              logger.info("Egress check passed")
              原样返回 data
```

| 步骤 | 文件:函数 | 作用 |
|---|---|---|
| 盲化 | `tokenizer.py:tokenize()` | HMAC-SHA256(id_card, salt) → 64字符不可逆hash |
| 收集 | `egress_filter.py:_collect_strings()` | 递归遍历JSON收集所有字符串值 |
| 扫描 | `egress_filter.py:scan_response()` | 正则匹配PII模式，白名单过滤已知安全值 |
| 阻断 | `egress_filter.py:wrap_response()` | 发现PII→阻断响应+告警日志 |

## 功能九：前端 Web 界面

**目标**：提供 Web SPA 界面，支持提交查询、查看候选方案、选择方案执行、实时查看执行进度。

### 涉及的文件

```
coordinator/static/index.html  → 主页面
coordinator/static/app.js      → 应用逻辑（查询提交、方案展示、执行控制）
coordinator/static/render.js   → 渲染逻辑（方案卡片、步骤列表、结果展示）
coordinator/static/style.css   → 样式
coordinator/app.py             → 静态文件挂载 + SPA路由
```

### 前端交互流程（三步式设计）

```
coordinator/app.py: app.mount("/static", StaticFiles)
coordinator/app.py: index() → FileResponse("static/index.html")

用户在浏览器访问 http://host:8000/ →
    加载 index.html →
    加载 app.js + render.js + style.css →
    ↓
[1] 用户输入自然语言查询 + 点击"解析查询":
    POST /api/query {"query":"..."} →
    返回 {query_id, query_ast, plans:[]}  ← 仅解析，不生成方案
    render.js 渲染:
      · 左侧：解析结果（筛选条件 + 聚合目标）
      · 右侧：占位区 + "⚡ 生成对比方案" 按钮
    ↓
[2] 用户点击"生成对比方案":
    POST /api/query/{id}/generate-plans →
    返回 {query_id, plans:[...]}（含友好描述、步骤列表、预估耗时）
    render.js 渲染:
      · 右侧：4个候选方案卡片（含推荐标识、DAG预估耗时、外传数据量）
      · 方案自动选中首个（推荐方案）
      · 底部操作栏：["📝 生成方案SQL"] ["▶ 执行所选方案"]
      · ⏱ 原子操作耗时分解 此时不显示
    ↓
[3a] 用户点击某方案 → 高亮选中 → 原子分解区不显示（未执行）
    ↓
[3b] 用户点击"📝 生成方案SQL":
    POST /api/query/{id}/sql/{plan_id} →
    Worker /explain 端点返回各阶段的展示 SQL（不执行查询）
    render.js 渲染:
      · 左侧解析结果下方：各阶段 SQL 语句卡片
        · filter/aggregate 阶段：实际模拟 SQL
        · intersect 阶段：合成描述（如 "-- Coordinator侧求交：2路Token集合取交集"）
        · compute 阶段：合成描述（如 "-- 主控汇总计算：合并1路聚合结果，最终AVG"）
      · 每个 SQL 卡片显示：阶段ID、执行位置、阶段类型
    ↓
[3c] 用户点击"▶ 执行所选方案":
    POST /api/query/{id}/execute_with_plan/{pid} →
    执行 DAG + WebSocket 实时推送
    render.js 渲染:
      · 查询结果卡片（大数值：N人，平均值 ¥xx）
      · 左侧 SQL 区：实际执行的各阶段 SQL（含 intersect/compute 描述，完整执行顺序）
      · ⏱ 原子操作耗时分解：显示（含实际耗时，可对比预估）
    ↓
[3d] 执行后切换方案：
    · 点击不同方案 → 原子分解区更新（显示该方案的预估 + 之前的实际耗时）
```

| 组件 | 文件 | 作用 |
|---|---|---|
| 主页面 | `static/index.html` | SPA 入口，提供查询输入框、方案面板、结果面板的DOM结构 |
| 业务逻辑 | `static/app.js` | API调用（/api/query, /api/query/{id}/execute等）、WebSocket连接管理、状态管理 |
| 渲染 | `static/render.js` | 将JSON数据渲染为可视组件（方案卡片含步骤、进度条、结果卡片、SQL展示） |
| 样式 | `static/style.css` | 界面美化（方案卡片、步骤列表、进度动画、结果面板） |
