# LLM 分布式查询系统 — 项目结构文档

> 生成日期：2026-06-28

---

## 一、项目概述

本系统是一个**联邦式（Federated）分布式查询系统**，核心思路是：

1. 用户用自然语言描述查询需求
2. Coordinator（主控节点）解析查询，生成多个候选执行计划（Plan），评估成本并排序
3. 用户选择执行方案后，Coordinator 调度各 Worker 执行筛选/聚合，最终汇总结果
4. 各 Worker 之间通过**HMAC-SHA256 盲化 Token**（人员标识的哈希）进行隐私安全的跨库求交

**隐私保护机制**：人员身份证号在离开 Worker 之前先经过 HMAC-SHA256 哈希盲化，Coordinator 永远看不到原始身份证号。

## 三、Coordinator（主控节点）模块详解

### 3.1 `coordinator/app.py` — FastAPI 主应用

**职责**：Coordinator 的主入口，提供 REST API、WebSocket、认证中间件、查询生命周期管理。

| 函数/类 | 类型 | 功能说明 |
|---|---|---|
| `WORKER_URLS` | 全局变量 | 从环境变量 `WORKER_URLS` 解析各 Worker 的 URL 映射（如 `worker_a → http://worker_a:8001`） |
| `queries` | 全局变量 | 内存中的查询存储字典 `{query_id: query_data}` |
| `ws_connections` | 全局变量 | 活跃 WebSocket 连接字典 `{query_id: [WebSocket]}` |
| `_cleanup_expired_queries()` | 函数 | 清理超过 TTL（默认3600秒）的过期查询条目，返回过期 query_id 列表 |
| `_cleanup_ws_connections()` | 异步函数 | 关闭并移除过期/孤立查询的 WebSocket 连接 |
| `_cleanup_loop()` | 异步函数 | 周期性后台任务：每 `QUERY_CLEANUP_INTERVAL`（默认300秒）运行一次清理 |
| `AuthMiddleware` | 类 | 纯 ASGI 中间件，从 HTTP Header 中提取 `Bearer <token>` 进行认证。在 body 读取之前注入，不会影响 FastAPI 的 body 解析。公开路径（`/`、`/register`、`/api/schema` 等）无需认证 |
| `ws_event_callback()` | 异步函数 | 向指定 `query_id` 的所有 WebSocket 连接推送事件，自动清理断开的连接 |
| `lifespan()` | 异步上下文管理器 | 应用生命周期：启动时打印 Worker URL 信息并启动清理循环；关闭时取消清理任务 |
| `register_worker()` | POST `/register` | Worker 注册端点，调用 `global_schema.register_worker()` 注册 Worker 元数据 |
| `get_schema()` | GET `/api/schema` | 返回全局 Schema 视图（Worker 列表 + 字段列表）给前端 |
| `submit_query()` | POST `/api/query` | **解析端点**（仅解析，不生成方案）：接收自然语言查询 → 调用 `parse_query()` 解析 → 返回 query_id 和解析结果（plans 为空）。方案生成延后到独立的 `/generate-plans` 端点 |
| `generate_plans()` | POST `/api/query/{id}/generate-plans` | **方案生成端点**：对已解析的查询调用 `generate_and_rank_plans()` → 存储方案 → 返回候选方案列表 |
| `generate_plan_sql()` | POST `/api/query/{id}/sql/{plan_id}` | **SQL 预览端点**：通过 Worker 的 `/explain` 端点获取各阶段的展示 SQL，不执行查询 |
| `get_plans()` | GET `/api/query/{id}/plans` | 获取某查询的详细候选方案（含 stages、stage_costs 等） |
| `execute_query()` | POST `/api/query/{id}/execute` | 使用推荐方案（plan[0]）执行查询 |
| `execute_query_with_plan()` | POST `/api/query/{id}/execute_with_plan/{pid}` | 使用指定方案执行查询 |
| `_execute_plan()` | 异步函数 | **执行核心**：创建 `DAGScheduler` → 执行计划（方案已在功能四中修复，无需再次修复）→ 通过 WebSocket 推送最终结果 |
| `websocket_endpoint()` | WS `/ws/{query_id}` | WebSocket 端点，支持 token 认证、心跳 ping/pong |
| `index()` | GET `/` | 提供前端 SPA 的 `index.html` |

**启动方式**：`uvicorn.run(app, host="0.0.0.0", port=8000)`

### 3.2 `coordinator/nl_parser.py` — 自然语言查询解析器

**职责**：将用户的中文自然语言查询转换为结构化的 QueryAST（筛选条件 + 聚合目标）。采用三层流水线架构。

#### Layer 1：LLM 解析

| 函数 | 功能说明 |
|---|---|
| `_build_llm_prompt(user_query, schema_text)` | 构建 LLM 提示词：包含全局数据视图（Schema 文本）和查询规则（操作符映射、年龄规则、"近N年"规则、多值 IN 规则等），要求输出严格 JSON |
| `parse_with_llm(user_query, schema_text)` | 调用 OpenAI 兼容 API（支持任意 LLM API Base）进行语义解析。发送 system prompt + user prompt，temperature=0.1 保证确定性。自动去除 markdown 代码块标记后解析 JSON。失败返回 None 触发规则回退 |

#### Layer 2：锚定与值校验

| 函数 | 功能说明 |
|---|---|
| `anchor_and_validate(parsed, global_schema)` | 对 LLM/规则解析结果进行字段路由和值校验：（1）将字段名解析到实际逻辑字段（含别名解析）；（2）找到该字段所属的 Worker；（3）对枚举类字段的值进行模糊匹配校准；（4）对聚合字段进行 Worker 路由。特殊处理：`COUNT(person_token)` 的聚合 Worker 从筛选 Worker 派生 |
| `_fuzzy_match_field(alias, global_schema)` | 模糊匹配字段名：先精确匹配逻辑字段名，再匹配别名 |
| `_fuzzy_match_value(value, known_values)` | 模糊匹配字段值：在已知值域中查找子串匹配 |

#### Layer 3：验证

| 函数 | 功能说明 |
|---|---|
| `validate_parsed_query(routed)` | 验证解析结果的完整性和合法性：（1）每个筛选字段必须能路由到数据源；（2）操作符必须合法；（3）聚合字段必须能路由（`COUNT(person_token)` 例外） |

#### 规则回退解析器

| 函数 | 功能说明 |
|---|---|
| `parse_with_rules(user_query, global_schema)` | **当 LLM 不可用时的规则回退**。内置 10+ 种正则模式匹配：研究方向、性别、机构类型、职称（含"工程师及以上"的 gte 语义）、海外经历、留学国家（支持"美国或德国"多国 IN 语义）、获奖级别（含"省级以上"的 gte 语义）、年龄范围、年份范围、"近N年"等。聚合模式覆盖 avg/max/min/sum/count。**去重与冲突解决**：相同字段的 eq 合并为 in，优先级 in > gte/lte > gt/lt > eq > neq |

#### 主入口

| 函数 | 功能说明 |
|---|---|
| `parse_query(user_query, global_schema)` | **主入口**：LLM 优先 → 规则回退 → 锚定校验 → 返回完整 QueryAST `{filters, aggregation, valid, errors, parsed_by}` |

### 3.3 `coordinator/schema_manager.py` — 全局 Schema 管理器

**职责**：维护所有 Worker 注册后的全局逻辑字段视图，提供字段路由、别名解析、值域查询等功能。

| 类/方法 | 功能说明 |
|---|---|
| `GlobalSchema` | 全局 Schema 单例类 |
| `__init__()` | 初始化四个核心数据结构：`workers`（Worker 信息）、`field_index`（逻辑字段→Worker ID 列表）、`alias_index`（别名→逻辑字段名）、`field_details`（逻辑字段→元数据） |
| `register_worker(worker_data)` | **注册 Worker**：接收 Worker 上报的逻辑字段元数据（不含物理列名），建立字段索引、别名索引、字段详情（类型、值域、是否加密）。多 Worker 的同名字段值域自动合并去重 |
| `get_workers_for_field(field_name)` | 根据逻辑字段名或别名查找所属 Worker ID 列表 |
| `get_field_by_alias(alias)` | 别名→逻辑字段名解析 |
| `get_field_type(field_name)` | 获取字段类型（enum/token/text/derived） |
| `get_field_values(field_name)` | 获取字段的已知值域列表 |
| `get_all_fields_summary()` | 返回所有字段的汇总信息（给前端使用） |
| `get_workers_summary()` | 返回所有 Worker 的汇总信息（含字段列表、行数、扫描延迟基线） |
| `to_prompt_text()` | 生成供 LLM 使用的全局 Schema 文本描述 |

**单例实例**：`global_schema = GlobalSchema()` — 模块级全局单例

### 3.4 `coordinator/scheduler.py` — DAG 调度器

**职责**：按照执行计划的 DAG（有向无环图）拓扑结构，调度各阶段在对应 Worker 上执行，并通过 WebSocket 实时推送事件。

| 类/方法 | 功能说明 |
|---|---|
| `DAGScheduler` | DAG 执行调度器 |
| `__init__(worker_urls, event_callback)` | 初始化：Worker URL 映射、事件回调函数、结果缓存 `results`、阶段耗时 `stage_times` |
| `set_query_id(qid)` | 设置当前查询 ID |
| `_push_event(event, data)` | 向 WebSocket 推送事件（自动附加时间戳） |
| `execute_plan(plan)` | **主执行循环**：循环检测依赖就绪的阶段 → 分组执行（并发组用 `asyncio.gather` 并行，串行阶段逐个执行）→ 查找 compute/aggregate 阶段结果作为最终输出 → 为**所有**阶段构建 SQL 日志（filter/aggregate 用实际 SQL，intersect/compute 用合成描述）→ 推送完成事件 → 返回结果 |
| `generate_sql(plan)` | **SQL 预览**：遍历所有阶段，对 filter/aggregate 阶段调用 Worker 的 `/explain` 端点获取展示 SQL，对 intersect/compute 阶段合成描述文本。不执行任何查询 |
| `_execute_stage(stage)` | **执行单个阶段**：根据 `type` 分发到 `_do_filter` / `_do_intersect` / `_do_aggregate` / `_do_compute`。记录耗时，存储结果，推送阶段开始/完成/错误事件 |
| `_do_filter(stage)` | **筛选阶段**：向指定 Worker 的 `/filter` 端点发送谓词，获取盲化 Token 列表 |
| `_do_intersect(stage)` | **求交阶段**：若在 Coordinator 侧执行 → 对所有上游 Token 集合做哈希集合交集运算（`&`）；若在 Worker 侧（数据下推）→ 将所有上游 Token 合并去重后返回（Union，由 Worker 本地匹配） |
| `_do_aggregate(stage)` | **聚合阶段**：将求交后的 Token 列表发送给聚合 Worker 的 `/aggregate` 端点，获取 sum/count/min/max/value |
| `_do_compute(stage)` | **汇总阶段**（纯 Coordinator 侧计算）：从上游聚合结果计算最终值。avg 使用 Worker 的预计算 value（支持稀疏字段如年终奖的非零均值）；sum/min/max/count 直接从上游累加或取极值。特殊处理 `coordinator_count`：主控直接计数 Token |
| `_summarize_result(result)` | 生成阶段结果的人类可读摘要 |

### 3.5 `coordinator/planner/` — 查询规划器子模块

#### `__init__.py`
- 包入口，导出 `generate_and_rank_plans`

#### `orchestrate.py` — 规划流水线编排

| 函数 | 功能说明 |
|---|---|
| `generate_and_rank_plans(query_ast, workers_summary, worker_urls)` | **完整规划流水线**：<br>1. `run_precheck()` — 预查各 Worker 命中数<br>2. `_enumerate_all_plans()` — 穷举所有合法计划拓扑<br>3. `generate_plans_with_llm()` — LLM 补充生成（可选）<br>4. `_merge_plans()` — 合并去重 LLM 生成的新计划<br>5. `_optimize_coordinator_count()` — COUNT(person_token) 优化<br>6. `compute_cost()` — 为每个计划计算成本<br>7. `_generate_friendly_description()` — 生成用户友好描述<br>8. `rank_plans()` — 按成本排序<br>9. 按 `friendly_description` 去重<br>10. 重新编号为 P1..Pn<br>11. 返回 Top 4 |

#### `enumeration.py` — 穷举式计划枚举

| 函数 | 功能说明 |
|---|---|
| `_optimize_coordinator_count(plan, query_ast)` | **COUNT 优化**：当聚合为 `COUNT(person_token)` 时，移除 aggregate 阶段，让 compute 阶段直接从上游 Token 求交结果计数（主控侧直接统计，无需发给 Worker 聚合） |
| `_enumerate_all_plans(query_ast, workers_summary, precheck_counts)` | **穷举所有合法计划拓扑**：<br>- 无筛选Worker → 1种（直接聚合）<br>- 单个筛选Worker → 1种（单节点查询）<br>- 2+筛选Worker → 穷举所有组合：<br>&emsp;• 并行过滤器 + 求交位置（coordinator / 各filter worker / agg worker）<br>&emsp;• 串行过滤器（全排列）× 求交位置<br>每个计划包含 stages：filter → intersect → aggregate → compute |
| `_generate_plans_rule_based(query_ast, workers_summary, precheck_counts)` | **规则生成回退**：生成固定4种拓扑（P1并行、P2串行A→B、P3串行B→A、P4数据下推），当 LLM 不可用或返回不足时使用 |

#### `generation.py` — LLM 辅助计划生成

| 函数 | 功能说明 |
|---|---|
| `generate_plans_with_llm(query_ast, workers_summary, precheck_counts)` | 调用 LLM API 生成4种候选计划拓扑。失败或返回不足时回退到 `_generate_plans_rule_based()`。结果经过 `_validate_and_repair_plan()` 验证修复 |

#### `prompt.py` — LLM Prompt 构建

| 函数 | 功能说明 |
|---|---|
| `_build_plan_prompt(query_ast, workers_summary, precheck_counts)` | 构建详细的 LLM 提示词：包含查询结构、Worker 信息、命中数预查结果、网络 RTT 信息、关键约束（filter 只能在有谓词的 Worker 上、aggregate 必须在聚合数据 Worker、coordinator 无数据库等）、4种方案模板（P1并行、P2串行A→B、P3串行B→A、P4数据下推） |

#### `precheck.py` — 预查命中计数

| 函数 | 功能说明 |
|---|---|
| `run_precheck(query_ast, worker_urls)` | **并行预查**：向每个有筛选谓词的 Worker 的 `/count` 端点发送谓词，获取命中行数。用于后续成本估算。所有 Worker 并行查询（`asyncio.gather`），失败时回退为 100 |

#### `cost_model.py` — 成本估算模型

| 函数 | 功能说明 |
|---|---|
| `compute_cost(plan, workers_summary, precheck_counts, network_rtt_ms=20)` | **精细化成本估算**：<br>- Filter 阶段：数据库扫描（命中数/总行数 × 扫描延迟）+ 网络传输（RTT + Token数据量 × 每Token传输时间）<br>- Intersect 阶段：哈希集合求交 ~3ms + 可选网络往返<br>- Aggregate 阶段：全表扫描（热缓存 0.4× 冷基线）+ HMAC 逐行匹配（每行 ~1μs）+ 网络往返<br>- Compute 阶段：固定 1ms<br>考虑并发组（取 max）vs 串行（求和） |
| `rank_plans(plans)` | 按 `estimated_cost_ms` 升序排列，第一个标记 `recommended=True` |

#### `validation.py` — 计划验证与修复

| 函数 | 功能说明 |
|---|---|
| `_validate_and_repair_plan(plan, valid_workers, query_ast)` | 验证并修复计划结构：（1）filter/aggregate 不能在 coordinator 上执行；（2）compute 必须在 coordinator；（3）移除无谓词的 filter 阶段；（4）更新依赖引用；（5）**自动插入缺失的 intersect 阶段**（2+ 不同 Worker 的 filter 但没有 intersect） |
| `repair_execution_plan(plan, query_ast, valid_worker_ids)` | **执行前统一修复**：整合了原 `_execute_plan()` 中的修复逻辑。<br>1. 为各 stage 填充 predicates 和 agg 信息<br>2. 移除空谓词的 filter 阶段<br>3. **合并同 Worker 的重复 filter 阶段**（LLM 可能为每个条件生成一个 filter stage）<br>4. 更新依赖关系<br>5. 自动插入缺失的 intersect 阶段 |
| `_plan_topology_signature(plan)` | 生成计划的规范化拓扑签名（用于去重），通过 (stage类型, 位置, 并发组, 依赖关系) 的排序元组表示 |
| `_merge_plans(existing, new_plans)` | 合并两个计划列表，按拓扑签名去重。新出现（LLM 生成但枚举没覆盖的）计划会保留 |

#### `description.py` — 用户友好描述生成

| 函数 | 功能说明 |
|---|---|
| `_generate_friendly_description(plan, workers_summary)` | **核心功能**：从计划 stages 自动生成用户可读的步骤说明。<br>识别4种拓扑：并行查询、串行查询、数据下推、直接统计。<br>生成中文数字标注的步骤列表（"第一步：...；第二步：..."）。<br>智能处理：单Worker时不生成"同时在"语义；同Worker连续filter不重复显示；区分求交位置（中心/本地/聚合节点）生成不同描述。<br>返回 `{friendly_name, friendly_description, steps}` |

## 四、Engine（Worker 引擎）模块详解

### 4.1 `engine/app.py` — Worker FastAPI 应用

**职责**：每个 Worker 运行此代码，启动时向 Coordinator 注册，提供筛选/计数/聚合端点。

| 函数/类 | 功能说明 |
|---|---|
| `lifespan()` | **启动生命周期**：加载 mapping.yaml → 测试数据库连接（5次重试）→ 运行基线测试（COUNT(*) + 全表扫描延迟） → 构建注册负载（仅逻辑字段元数据，不泄漏物理列名）→ 向 Coordinator 注册（最多30次重试，每2秒一次） |
| `egress_check(data)` | 在返回响应前调用出口过滤器，检测 PII 泄露并拦截 |
| `_should_debug_sql()` | 检查 `DEBUG_SQL` 环境变量，控制是否在响应中包含物理 SQL（默认关闭） |
| `_build_logical_display_sql(predicates, stype, agg_field, agg_func)` | **构建逻辑 SQL 展示语句**：仅使用 mapping.yaml 中的逻辑字段名和表名，构建用户可读的展示 SQL（如 `SELECT person_token FROM talent WHERE gender = '女'`），绝不暴露物理列名 |
| `health()` | GET `/health` — 健康检查 |
| `explain(req)` | POST `/explain` — **SQL 预览**：接收谓词/聚合参数，仅返回展示 SQL 不执行查询。用于前端的"生成方案SQL"功能 |
| `count(req)` | POST `/count` — 命中数预查：接收谓词列表，执行 `SELECT COUNT(*)` 返回标量 |
| `filter_endpoint(req)` | POST `/filter` — **核心筛选端点**：<br>1. 将逻辑谓词翻译为物理 SQL<br>2. 查询数据库获取原始 id_card<br>3. 对每条 id_card 执行 HMAC-SHA256 盲化<br>4. 返回盲化 Token 列表<br>5. 生成用户可读的逻辑 SQL 展示<br>6. 通过出口过滤器检查后返回 |
| `aggregate(req)` | POST `/aggregate` — **聚合端点（盲匹配）**：<br>1. 接收 Coordinator 传来的盲化 Token 集合<br>2. **MySQL/PostgreSQL**：数据库侧 HMAC（`SHA2(CONCAT(salt, col), 256)` 或 `encode(sha256(...), 'hex')`），SQL `WHERE` 中直接匹配，聚合在 DB 内完成<br>3. **SQLite**：无法在 DB 内做 HMAC，全表取出后在 Python 侧逐行 HMAC → 集合匹配 → 聚合<br>4. 返回 sum/count/min/max/value + 逻辑 SQL 展示 |

### 4.2 `engine/db.py` — 数据库连接管理

**职责**：统一管理 MySQL、PostgreSQL、SQLite 三种数据库的连接和查询。

| 函数 | 功能说明 |
|---|---|
| `get_db_type()` | 读取 `DB_TYPE` 环境变量 |
| `quote_identifier(name, db_type)` | **SQL 标识符引用**：MySQL 用反引号（`` ` ``），PostgreSQL/SQLite 用双引号（`"`）。防止标识符注入，自动跳过已引用的标识符 |
| `get_connection()` | **数据库连接工厂**（单例缓存）：<br>- SQLite：只读 URI 模式（`file:...?mode=ro`），10次重试，验证 schema 可访问<br>- MySQL：通过 `mysql.connector` 连接<br>- PostgreSQL：通过 `psycopg2` 连接，使用 `RealDictCursor` |
| `execute_query(sql, params)` | 执行查询并返回 `list[dict]` 格式的所有行 |
| `execute_scalar(sql, params)` | 执行查询并返回单个标量值 |

### 4.3 `engine/sql_builder.py` — SQL 构建器

**职责**：将 Coordinator 传来的逻辑谓词翻译为数据库特定的物理 SQL。这是隐私隔离的关键层——逻辑字段名到物理列名的映射仅在此发生。

| 类/函数 | 功能说明 |
|---|---|
| `_MappingCache` | 线程安全的映射缓存类，支持显示失效（`invalidate()`）用于测试 |
| `load_mapping(reload)` | 加载并缓存 mapping.yaml 文件 |
| `get_token_field(mapping)` | 查找映射中的 secret/token 字段定义（用于构建 Token 化的 SQL） |
| `get_field_by_logical(logical_name)` | 按逻辑字段名或别名查找字段定义 |
| `get_field_by_alias(alias_text)` | 按别名查找字段定义 |
| `translate_value_to_physical(field_def, value)` | **值翻译**：将展示值（如"物联网"→"01"）翻译为物理编码。支持正向和反向映射查找 |
| `translate_operator(op)` | 操作符翻译：`eq→=`, `neq→!=`, `gt→>`, `gte→>=`, `lt→<`, `lte→<=`, `in→IN` |
| `build_where_clause(predicates, table_alias)` | **WHERE 子句构建**：遍历谓词 → 查字段定义 → 翻译值 → 处理派生字段表达式 → 生成参数化 SQL。支持 IN 多值、派生字段包装、标识符引用 |
| `build_filter_query(predicates, salt_placeholder)` | **筛选查询构建**：MySQL 用 `SHA2(CONCAT(salt, col), 256)` 在 DB 内做 HMAC 盲化；PostgreSQL 用 `encode(sha256(...), 'hex')`；SQLite 直接取原始列（HMAC 在 Python 侧做） |
| `build_count_query(predicates)` | 构建 `SELECT COUNT(*) FROM table WHERE ...` 查询 |
| `build_aggregate_query(tokens, agg_field, agg_func)` | **聚合查询构建（盲匹配）**：<br>- MySQL/PostgreSQL：`WHERE HMAC_EXPR IN (token1, token2, ...)` 在数据库内完成盲匹配和聚合<br>- SQLite：返回全表数据，由调用方在 Python 侧做 HMAC 匹配 |

---

### 4.4 `engine/egress_filter.py` — 出口过滤器

**职责**：在 Worker 响应离开前扫描 PII（个人身份信息），防止原始身份证号、手机号、邮箱泄露。

| 函数 | 功能说明 |
|---|---|
| `_collect_strings(data)` | 递归遍历 JSON 结构，收集所有字符串值（跳过数值和布尔值，避免 HMAC 哈希误报） |
| `scan_response(data)` | 用正则扫描 PII 模式：18位身份证号、手机号、邮箱。已知安全值（如"物联网"、"教授"等字段枚举值）在 `SAFE_VALUES` 白名单中，不会被误报 |
| `wrap_response(data)` | 响应包装器：调用 `scan_response`，若发现 PII 泄露则拦截并记录告警日志 |

---

### 4.5 `engine/tokenizer.py` — HMAC-SHA256 Token 生成器

**职责**：将身份证号盲化为不可逆的 HMAC-SHA256 哈希 Token，保证跨 Worker 的同一身份证号生成相同 Token（同盐），同时无法从 Token 反推原始身份证号。

| 函数 | 功能说明 |
|---|---|
| `get_salt()` | 从 `SALT` 环境变量读取盐值。所有 Worker 必须共享同一盐值。未设置时抛出 `RuntimeError` |
| `tokenize(id_card)` | **核心盲化**：`hmac.new(salt.encode('utf-8'), id_card.encode('utf-8'), hashlib.sha256).hexdigest()` → 64字符十六进制字符串 |

## 八、系统数据流总览

```
用户自然语言查询
      ↓
Coordinator: parse_query()              # NL解析 → QueryAST（仅解析）
      ↓
前端显示解析结果，用户点击"生成对比方案"
      ↓
Coordinator: run_precheck()             # 并行预查各Worker命中数
      ↓
Coordinator: _enumerate_all_plans()     # 穷举所有候选执行计划
      ↓
Coordinator: generate_plans_with_llm()  # LLM补充生成（可选）
      ↓
Coordinator: repair_execution_plan()    # 修复计划结构（在成本估算前）
      ↓
Coordinator: compute_cost() + rank()    # 成本估算 + 排序 → Top 4
      ↓
Coordinator: 返回候选方案给前端
      ↓
用户选择方案 → 可选: 生成方案SQL 或 执行所选方案
      ↓
Coordinator: DAGScheduler.generate_sql() 或 execute_plan()
      ↓
     ┌─ Worker A: /filter ──→ [tokens] ──┐
     ├─ Worker B: /filter ──→ [tokens] ──┤
     │         ↓                          │
     │   Coordinator: intersect()         │  (或 Worker 侧 Union)
     │         ↓                          │
     └─ Worker C: /aggregate ← tokens ────┘
              ↓
     Coordinator: compute()               # 汇总最终结果
              ↓
     WebSocket: 实时推送 → 前端展示结果
```

**隐私保护要点**：
1. Worker 注册时只上报逻辑字段元数据，不暴露物理列名
2. 原始 id_card 在 Worker 内通过 HMAC-SHA256 盲化后才离开
3. Coordinator 只能看到盲化 Token，无法反向推导原始身份证号
4. 出口过滤器在每个 Worker 响应中扫描 PII 模式
5. 展示 SQL 仅使用逻辑字段名，物理列名不出 Worker
